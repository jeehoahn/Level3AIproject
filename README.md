# 허프만 코딩 팀 프로젝트 — 공통 GUI + 독립적인 두 알고리즘

## 바로 실행

Windows PowerShell 예시(프로젝트 압축 해제 후):

```powershell
cd huffman_team_project_auto_validation
py -m pip install -r requirements.txt
py main.py
```

**새 필수 패키지:** `psutil` (CPU가 아니라 Python 프로세스 RSS 측정용). 설치 명령은
`requirements.txt`에서 PySide6와 psutil을 모두 설치합니다. GUI가 없는 환경에서는
`python -m pip install psutil`로 CLI와 자동 테스트만 실행할 수 있습니다.

## 이번 버전: 실행 시 자동 사전 검사 · 1GB 이상 스트리밍 · 메모리 기본 해제

GUI의 **`선택한 원본 파일 점검`**, **`enwik9 (1GB) 스트리밍 사전 점검`**
버튼과 수동 점검 영역을 제거했습니다. 별도 검사 버튼을 누를 필요가 없으며,
**`압축만 수행`**, **`압축 + 복원 + 손실률 검사`**, **`.huf 파일 복원`**, **`실험 시작`**
각 버튼을 누르면 엔진에서 자동으로 검사합니다.

- **압축 시작 시:** 원본 경로 존재·일반 파일 여부·읽기 가능 여부·원본 크기/지원 범위,
  입력/출력 경로 충돌, 출력 폴더에 임시 파일을 생성할 수 있는지 검사합니다.
- **복원 시작 시:** `.huf` 파일 열기·헤더(MAGIC/버전/길이) 검증·알고리즘 지원,
  복원 크기/지원 범위, 출력 폴더 접근과 원본 직접 비교 파일(있는 경우) 확인.
- **실행 중/후:** 파일 읽기·쓰기 실패, 스트리밍 인코딩/디코딩 오류,
  SHA-256 및 복원 크기 검증을 별도 수행합니다. `압축 + 복원 + 손실률 검사`에서는
  원본 바이트와 직접 비교합니다. 실패 시 단계·종류·원인을 상세 결과·CSV·JSON에 기록합니다.
- **주의:** 사전 검사는 전체 파일을 다시 읽지 않습니다. 입력 내용을 스캔하는
  빈도·해시 계산 단계는 압축 실행의 일부입니다. 저장 공간 부족이나 실행 중
  파일 변경 등은 사전 검사만으로 보장할 수 없습니다.


**정적 허프만과 FGK 모두** 1MiB 단위 파일 입력을 처리하며,
압축 비트와 복원 파일은 버퍼를 사용하여 디스크로 직접 기록합니다.
원본과 복원본을 통째로 `read_bytes()` 하지 않습니다.
정적 허프만은 첫 번째 순회에서 빈도/UTF-8 문자 수/SHA-256을 계산하고,
두 번째 순회에서 압축합니다. FGK도 공통 보고용 빈도/해시를 위해 1회
사전 스캔한 뒤 실제 적응형 압축을 시작합니다. 복원 도중 원본 비교도
청크별로 진행합니다. 파일 포맷은 종전 **HUF1 v1** 그대로입니다.

- **512MiB 제한 제거:** 64비트 원본 크기 필드를 사용하여 1,000,000,000B
  이상의 파일을 스트리밍으로 압축/복원하도록 했습니다. 파일 크기 사전 검사는
  메모리 할당 없이 수행하고 RAM 주의 메시지도 제공합니다. 대용량 처리에는
  충분한 디스크 공간과 시간이 필요합니다.
- **성공/실패 및 오류 원인:** 압축·복원 단계, 파일 접근/헤더/손상/무결성
  등의 오류를 상세 결과·CSV·JSON에 기록합니다. 손상·불일치 출력 파일은
  최종 경로에 남기지 않습니다. 하나의 실험이 실패해도 일괄 실험은 계속됩니다.
- **Python 메모리 및 RSS:** GUI의 `알고리즘 메모리 측정`은 **기본 해제**.
  선택한 경우에만 `tracemalloc` Python 추적 피크, `psutil` 10ms 간격 관측
  프로세스 RSS 피크 및 실행 시작 대비 증가량을 기록합니다. `RSS`는
  프로세스 전체 메모리이며, 짧은 순간의 실제 최대치를 놓칠 수 있습니다.
- **성능 시간의 의미:** 스트리밍 구현에서 `*_algorithm_sec`는 **스트리밍
  인코더/디코더 호출 시간으로, 그 안의 청크 파일 입출력도 포함합니다.**
  파일 전체 시간은 별도로 나타내며 사전 빈도/해시 계산·저장 확정 등을 포함합니다.
  순수 CPU 연산 시간이라고 해석하지 마세요.
- **대용량 복원 반환 형식:** `decompress_file()`의 첫 반환값은 결과 기록이고,
  두 번째 반환값은 작은 파일(≤4MiB)일 때 `bytes`, 큰 파일은 `None`입니다.
  큰 파일의 실제 복원본은 지정한 `destination`에 정상 저장됩니다.
- **FGK 실행 시간 주의:** FGK는 Python에서 각 바이트마다 트리를 업데이트하므로
  enwik9(1GB)에 매우 오래 걸릴 수 있습니다. 스트리밍 메모리 지원과
  현실적인 실행 속도는 다른 문제입니다.
- **기존 사용자 알고리즘 호환:** 과거 `encode(bytes)/decode(bytes)`만 구현한
  추가 알고리즘은 작은 파일(≤16MiB)에서 작동합니다. 대용량 압축을 지원하려면
  `streaming_metadata`, `encode_stream`, `decode_stream` 세 메서드를 추가해야 합니다.

- 기존 및 신규 자동 테스트 **32개 통과** (양 알고리즘의 빈 파일/한글/임의 바이트,
  구 HUF1 파일 호환, 청크 경계, 손상 파일, 기본 메모리 비활성화 확인).
- **1,000,000,000B 합성 0바이트 파일**에 대해 정적 허프만 스트리밍 압축,
  스트리밍 복원 및 원본 바이트 직접 비교까지 **성공 (불일치 0바이트)**.
  이 테스트는 단일 심볼 최적화 경로이며 **실제 enwik9 콘텐츠는 테스트하지
  않았습니다.** 따라서 enwik9 압축률/시간을 입증하는 실험이 아닙니다.

### GUI 이용 절차 (4개 탭)

1. **개별 파일 압축 / 복원** — 원본 파일과 알고리즘을 선택해 바로 실행합니다. 별도의 검사 버튼 없이 입력·출력·헤더 검사가 자동 수행되며, `.huf` 복원도 가능합니다. 완료/실패 결과는 **상세 결과 / 허프만 코드표** 탭에 기록됩니다.
2. **다중 파일 실험 / 비교** — 여러 실험 파일 및 알고리즘을 지정하면 조합별로 압축·복원·무손실 검증을 진행하고, 평균 비교표와 개별 결과표를 채웁니다. 결과표 행을 **더블클릭**하거나 **선택 실험 상세 보기** 버튼을 클릭하면 세 번째 탭으로 이동합니다.
3. **상세 결과 / 허프만 코드표** — 상단 `파일 · 알고리즘 · 실행 기록` 콤보박스에서 결과를 하나 선택합니다. 왼쪽에서 원본/압축 크기, 복원 손실률, SHA-256/바이트 검증, 시간·처리량·엔트로피 등 모든 세부 지표를 확인하고, 오른쪽에서 심볼별 빈도·코드·길이를 정렬/검색할 수 있습니다.
4. **결과 그래프 / 정렬** — `비교 지표`에서 압축률·압축 시간·복원 시간·스트리밍 인코더/디코더 구간 시간·압축/복원 피크 RSS·Python 추적 피크·엔트로피·헤더 크기·손실률 등 하나를 선택합니다. `정렬`에서 **값 큰 순 / 값 작은 순 / 파일명 오름차순 / 파일명 내림차순**을 고르고 `알고리즘` 필터를 설정합니다. **각 막대는 파일×알고리즘×실행 회차 하나를 의미합니다.** 막대 클릭 시 상세 결과로 이동하고, `그래프 PNG 저장`으로 보고서에 사용할 그림을 내보낼 수 있습니다.

**결과 누적 방식:** 개별 실행과 다중 파일 실험 결과 모두 같은 실행 기록 목록에 추가됩니다. 동일한 파일과 알고리즘을 재실행하면 이전 실행을 지우지 않고 별도 회차로 보관합니다. 앱 종료 후에도 비교하려면 세 번째 탭의 `상세 결과 JSON 저장`을 이용하세요. `기존 결과 JSON 불러오기`로 코드표까지 복구할 수 있습니다. `전체 결과 CSV 저장`은 누적된 모든 결과를 내보내며, 두 번째 탭의 `결과 CSV 내보내기`는 **가장 최근 일괄 실험** 결과만 내보냅니다.

**그래프 수치 누락:** `압축만 수행`에서는 복원 시간과 손실률이, 독립 `.huf` 복원에서는 원본과 직접 비교하는 손실률이 없을 수 있습니다. 선택한 지표가 없는 기록은 그래프에서 제외하고 제외 건수를 표시합니다. 용량 절감률이 음수이면 0 기준선 왼쪽에 막대를 그립니다. 빈 파일은 압축률이 정의되지 않아 제외될 수 있습니다.

**정확도 유의:** `복원 손실률 0%`는 반드시 원본 파일과 바이트 비교를 수행한 결과에만 해당합니다. 복원만 하는 경우 헤더에 저장된 SHA-256으로 무결성을 확인하지만 손실률을 임의로 0% 표시하지 않습니다.

## 조별원 역할 분리: 반드시 지킬 계약

**팀원 A**는 `algorithms/static_huffman.py`에서 자신의 구현을 자유롭게 개선할 수 있습니다. **팀원 B**는 `algorithms/adaptive_fgk.py`에서 자신의 구현을 수정할 수 있습니다. 두 코드는 기본 encode/decode 계약을 유지하면서 아래 스트리밍 메서드도 구현해야 1GB를 처리할 수 있습니다.

```python
from algorithms.base import Codec, PackedData, DecodedData

class MyCodec(Codec):
    id = 'my_new_codec'          # 변경하면 과거 압축 파일과 호환되지 않음
    name = '내 알고리즘 이름'
    description = '설명'

    def encode(self, data: bytes, progress=None) -> PackedData:
        # progress(0.0~1.0)를 가끔 호출하면 GUI 진행률이 갱신됩니다.
        # 페이로드는 반드시 BitWriter로 실제 비트 단위로 저장하세요.
        return PackedData(payload=b'', bit_length=0, metadata=b'',
                          codes={}, code_note='설명')

    def decode(self, payload: bytes, bit_length: int, metadata: bytes,
               original_size: int, progress=None) -> DecodedData:
        # 모든 유효 비트 소비 / 원본 바이트 완전 복원 / 잘못된 파일 예외 처리
        return DecodedData(data=b'', codes={}, code_note='설명')
```

**추가된 스트리밍 인터페이스:** `streaming_metadata(frequencies)`는 입력 빈도로
먼저 기록할 메타데이터를 반환합니다(정적: 256B 코드 길이, FGK: `b''`).
`encode_stream(source, target, original_size, metadata, progress)`는 입력을
청크로 읽고 압축 비트를 대상 파일에 기록하며 `StreamEncoded(bit_length,
 codes, code_note)`를 반환합니다. `decode_stream(source, target, payload_bits,
metadata, original_size, progress)`는 청크로 해석해 출력 파일에 복원하며
`StreamDecoded(codes, code_note)`를 반환합니다. 공통 GUI나 결과 모듈을
건드릴 필요가 없고 **두 알고리즘의 작업 영역은 각각 분리**됩니다.

새 클래스를 별도 파일에 만드는 경우 `algorithms/registry.py`의 `CODECS`에 한 번만 등록하면 GUI 콤보박스, 복원, 벤치마크, CSV에 자동 등장합니다. **`id`는 파일 포맷의 일부입니다**. 팀원 사이에서 ID 중복을 만들지 말고, 헤더 구조나 `bitstream.py`는 임의로 바꾸지 마세요.

### 정적 방식과 적응형 방식의 메타데이터 차이

- **정적(A)**: 입력 전체 빈도로 트리를 생성하고, 심볼별 코드 길이 256개를 파일 메타데이터에 저장합니다. 압축기는 canonical Huffman 코드를 만들고 복원기는 길이표만으로 동일한 코드를 재생성합니다.
- **적응형 FGK(B)**: NYT(Not Yet Transmitted) 노드와 동일한 교환/증가 규칙을 양측에서 사용합니다. 새 바이트를 만날 때 8비트 원시 바이트를 전송합니다. **초기 트리는 고정된 NYT 하나이므로 별도 정적 코드표가 복원에 필요하지 않습니다.** 파일의 알고리즘 ID와 버전이 복원 절차를 지정합니다. 코드표 화면은 전체 처리 완료 시점의 코드이며 중간 시점 코드는 바뀝니다.

> 채점자가 '압축 파일에 **정적 허프만 테이블 정보가 반드시 포함**되어야 한다'고 엄격히 해석한다면 A 방식이 그 요구에 직접 대응합니다. B는 FGK의 수학적 특성 때문에 동적 트리 재구성 방식임을 발표에서 설명해야 합니다.

## .huf 컨테이너 포맷(v1)

| 순서 | 크기 | 용도 |
| --- | ---: | --- |
| MAGIC `HUF1` | 4 byte | 형식 확인 |
| version | 1 byte | 형식 버전(현재 1) |
| 알고리즘 ID 길이 | 1 byte | ID 크기 |
| 원본 크기 | 8 byte | 복원할 바이트 수 |
| 유효 비트 길이 | 8 byte | 마지막 바이트 패딩 제외 |
| 메타데이터 크기 | 4 byte | 코드표 크기 |
| 원본 SHA-256 | 32 byte | 정확성 검증 |
| 알고리즘 ID | 가변 | `static` 또는 `fgk` |
| 알고리즘 메타데이터 | 가변 | 정적 256바이트 코드 길이표 / FGK는 빈 값 |
| 압축 페이로드 | 가변 | 8비트씩 결합된 바이트열, 끝자리 패딩 0 |

**헤더는 실제 파일 크기에 포함**됩니다. 58바이트 고정 헤더 + ID + 메타데이터이고 압축률을 계산할 때 헤더를 제외하는 일이 없습니다. 이 파일 포맷은 프로젝트 전용 포맷이며 표준 `.zip`/`.gz`와 호환되지 않습니다. 코드 구현에는 zlib/gzip/압축 패키지를 사용하지 않습니다. SHA-256은 압축 알고리즘이 아닌 무결성 검증에만 사용됩니다.

## 결과표 계산 공식

| 지표 | 계산 기준 |
| --- | --- |
| 용량 절감률 (%) | `(1 - 실제 .huf 크기 / 원본 크기) × 100` (음수면 오히려 커진 것) |
| 압축 배율 | `원본 크기 / 실제 .huf 크기` |
| 파일 평균 비트 수 | `실제 .huf 크기 × 8 / 원본 바이트 수` |
| 페이로드 평균 비트 수 | `패딩 제외 압축 유효 비트 수 / 원본 바이트 수` |
| 엔트로피 H(X) | `-Σ p(byte) × log2(p(byte))` (bit/byte) |
| 엔트로피 초과 비트 | `실제 페이로드 평균 - H(X)` |
| 엔트로피 대비 효율 (%) | `H(X) / 페이로드 평균 × 100` (분포 변화가 있는 FGK에선 100%를 넘을 수도 있으므로 참고값) |
| 헤더 비중 (%) | `헤더 크기 / 실제 .huf 크기 × 100` |
| 손실 바이트 수 | `원본·복원 파일에서 위치별 다른 바이트 + 길이 차이` |
| 손실률 (%) | `손실 바이트 수 / max(원본 크기, 복원 크기, 1) × 100` |
| 처리 시간 | `perf_counter()` 측정 (파일 읽기/쓰기 포함) |
| 처리량 | `원본 바이트 수 / 처리 시간 / 1,048,576` MiB/s |

- **손실률 0.000000%**는 `압축 + 복원 + 검사`에서 별도 복원 파일을 만든 뒤 원본과 바이트 단위 비교하여 확인합니다. **파일 손실 0과 압축률 증가는 별개의 값**입니다.
- 원본 파일이 없는 **독립적인 복원**에서는 헤더의 SHA-256과 크기 검증은 수행하지만, 손실률은 **'—'**로 표시합니다. 원본과 직접 비교하지 않고 손실률 0%라고 주장하지 않습니다.
- **빈 파일**은 엔트로피와 평균 비트를 0으로 놓고 비율이 정의되지 않는 값(용량 절감률 등)은 `—`로 표시합니다. 작은 파일은 헤더 때문에 오히려 크기가 늘어날 수 있습니다.
- 비트 단위 압축의 평균 코드 길이(Huffman)과 **헤더를 포함한 파일 평균 비트 수**는 구분합니다. FGK는 신규 심볼 NYT+8비트를 포함한 페이로드 실제 비트 수를 사용합니다.
- 손상된 파일(MAGIC, 길이, 패딩, 코드표, 출력 SHA 불일치 등)은 오류로 처리하고, 정확성이 검증되지 않으면 출력 파일을 저장하지 않습니다. 단, **내가 작성한 알고리즘의 자동 비교실험**에서는 복원 바이트가 달라도 오류로 중단하지 않고 실제 손실률/차이 바이트 수를 결과표에 **FAIL**로 남기며, 손상된 복원 파일은 저장하지 않습니다.

## 발표 실험 권장안

12개 샘플을 두 알고리즘으로 실행하면 총 **24회** 실험입니다. 각 파일의 원본 바이트 수/바이트 종류/엔트로피/절감률/헤더 비중/압축 시간/복원 시간을 CSV로 저장합니다. 압축률에는 헤더 비용이 포함됩니다. 정확성 검증은 전부 PASS(손실률 0%)여야 합니다. 실제 측정 시간은 CPU·저장장치·Python 버전에 따라 달라지므로 장비 사양과 Python 버전도 함께 보고서에 기록하세요.

**보고서 그래프 4종 추천 (4번째 탭은 단일 지표별 PNG 출력, 여러 지표의 같은 그래프 비교는 CSV로 별도 작성):** (1) 문자 수별 압축 시간, (2) 분포 유형별 실제 절감률, (3) 엔트로피와 페이로드 평균 비트 수, (4) A/B 알고리즘의 파일별 압축 및 복원 시간. 연속 실험 3회 이상 반복하여 평균/표준편차를 기록하면 성능 비교의 신뢰도가 높아집니다.

## 안전/예외 처리 및 한계

- 기본 입력 단위는 **바이트 0~255**입니다. UTF-8 한글은 문자당 여러 바이트가 될 수 있어 문자 엔트로피가 아니라 바이트 엔트로피가 출력됩니다.
- SHA-256은 청크 단위로 계산하며 원본 전체를 메모리에 적재하지 않습니다. 64비트 길이 헤더를 유지하지만 실제 파일 크기는 디스크 공간과 실행 시간의 제약을 받습니다.
- `FGK`는 이해와 검증에 초점을 둔 Python 구현으로 순수 파이썬에서 정적 허프만보다 느릴 수 있습니다. 입력이 크면 완료 시간이 길어질 수 있습니다.
- 압축 입력 파일을 우발적으로 덮어쓰지 않도록 경로 검사를 합니다. 복원 결과는 임시 파일에 기록하고 SHA-256/길이 검증을 통과해야 원자적으로 최종 저장합니다.
- 반복 실험의 평균 통계는 각 파일을 1회 측정한 값의 산술 평균입니다. 여러 반복의 표준편차는 별도 반복 실행/CSV 집계가 필요합니다.
- 운영체제 전체 RAM 사용률은 측정하지 않습니다. 프로세스 RSS와 Python 추적 메모리는 서로 정의가 다르므로 발표에서 구분하세요.
