# 허프만 코딩 팀 프로젝트 — 공통 GUI + 독립적인 두 알고리즘

## 바로 실행

Windows PowerShell 예시(프로젝트 압축 해제 후):

```powershell
cd huffman_team_project
py -m pip install -r requirements.txt
py main.py
```

GUI를 설치하기 어려운 환경에서는 **표준 라이브러리만으로** 압축, 복원, 검사, 실험을 실행할 수 있습니다.

```powershell
py cli.py verify test_corpus/50000_skewed_ascii.txt results/test.huf --algorithm static
py cli.py verify test_corpus/50000_skewed_ascii.txt results/test_fgk.huf --algorithm fgk
py cli.py decompress results/test.huf results/restored.txt
py -m unittest discover -s tests -v
```

데이터가 없는 경우 아래 생성 명령을 먼저 실행하세요.

```powershell
py scripts/make_test_data.py --output test_corpus
```

50,000자 / 100,000자 / 500,000자 각각에 대해 균일 ASCII, 편중 ASCII, 반복 패턴, 한글 문장 조합을 생성합니다(**총 12개 텍스트**). 한글은 UTF-8에서 글자 수와 바이트 수가 다를 수 있습니다. 샘플 문장은 AI가 작성했으며 길이 확장과 빈도 분포는 스크립트로 재현 가능하게 생성합니다.

### GUI 이용 절차

1. `개별 파일 압축/복원`에서 텍스트 파일과 A 또는 B 알고리즘을 고릅니다.
2. `압축 + 복원 + 손실률 검사`를 클릭하고 `.huf` 출력 경로를 고릅니다. 같은 폴더에 `_restored`를 붙인 복원 파일이 생성됩니다.
3. 아래 결과 영역에서 실제 용량 절감률, 엔트로피, 압축·복원 시간, SHA-256/바이트 비교 결과, 빈도표, 코드 길이를 봅니다.
4. `다중 파일 실험/비교`에서 여러 `.txt`를 추가하고 알고리즘을 체크한 다음 출력 폴더를 정하여 실행합니다.
5. `CSV 내보내기`를 클릭하면 각 파일별 결과를 엑셀에서 읽을 수 있는 UTF-8 BOM CSV로 저장합니다.
6. 외부에서 받은 `.huf`도 `복원` 버튼으로 열 수 있습니다. 복원 알고리즘은 파일 헤더에서 자동 판별됩니다.

## 조별원 역할 분리: 반드시 지킬 계약

**팀원 A**는 `algorithms/static_huffman.py`에서 자신의 구현을 자유롭게 개선할 수 있습니다. **팀원 B**는 `algorithms/adaptive_fgk.py`에서 자신의 구현을 수정할 수 있습니다. 두 코드는 반드시 아래 계약을 지킵니다.

```python
from algorithms.base import Codec, PackedData, DecodedData

class MyCodec(Codec):
    id = 'my_new_codec'          # 변경하면 과거 압축 파일과 호환되지 않음
    name = '내 알고리즘 이름'
    description = '설명'

    def encode(self, data: bytes, progress=None) -> PackedData:
        # progress(0.0~1.0)를 가끔 호출하면 GUI 진행률이 갱신됩니다.
        # 페이로드는 반드시 BitWriter로 실제 비트 단위로 저장하세요.
        return PackedData(payload=b'', bit_length=0, metadata=b'',
                          codes={}, code_note='설명')

    def decode(self, payload: bytes, bit_length: int, metadata: bytes,
               original_size: int, progress=None) -> DecodedData:
        # 모든 유효 비트 소비 / 원본 바이트 완전 복원 / 잘못된 파일 예외 처리
        return DecodedData(data=b'', codes={}, code_note='설명')
```

새 클래스를 별도 파일에 만드는 경우 `algorithms/registry.py`의 `CODECS`에 한 번만 등록하면 GUI 콤보박스, 복원, 벤치마크, CSV에 자동 등장합니다. **`id`는 파일 포맷의 일부입니다**. 팀원 사이에서 ID 중복을 만들지 말고, 헤더 구조나 `bitstream.py`는 임의로 바꾸지 마세요.

### 정적 방식과 적응형 방식의 메타데이터 차이

- **정적(A)**: 입력 전체 빈도로 트리를 생성하고, 심볼별 코드 길이 256개를 파일 메타데이터에 저장합니다. 압축기는 canonical Huffman 코드를 만들고 복원기는 길이표만으로 동일한 코드를 재생성합니다.
- **적응형 FGK(B)**: NYT(Not Yet Transmitted) 노드와 동일한 교환/증가 규칙을 양측에서 사용합니다. 새 바이트를 만날 때 8비트 원시 바이트를 전송합니다. **초기 트리는 고정된 NYT 하나이므로 별도 정적 코드표가 복원에 필요하지 않습니다.** 파일의 알고리즘 ID와 버전이 복원 절차를 지정합니다. 코드표 화면은 전체 처리 완료 시점의 코드이며 중간 시점 코드는 바뀝니다.

> 채점자가 '압축 파일에 **정적 허프만 테이블 정보가 반드시 포함**되어야 한다'고 엄격히 해석한다면 A 방식이 그 요구에 직접 대응합니다. B는 FGK의 수학적 특성 때문에 동적 트리 재구성 방식임을 발표에서 설명해야 합니다.

## .huf 컨테이너 포맷(v1)

| 순서 | 크기 | 용도 |
| --- | ---: | --- |
| MAGIC `HUF1` | 4 byte | 형식 확인 |
| version | 1 byte | 형식 버전(현재 1) |
| 알고리즘 ID 길이 | 1 byte | ID 크기 |
| 원본 크기 | 8 byte | 복원할 바이트 수 |
| 유효 비트 길이 | 8 byte | 마지막 바이트 패딩 제외 |
| 메타데이터 크기 | 4 byte | 코드표 크기 |
| 원본 SHA-256 | 32 byte | 정확성 검증 |
| 알고리즘 ID | 가변 | `static` 또는 `fgk` |
| 알고리즘 메타데이터 | 가변 | 정적 256바이트 코드 길이표 / FGK는 빈 값 |
| 압축 페이로드 | 가변 | 8비트씩 결합된 바이트열, 끝자리 패딩 0 |

**헤더는 실제 파일 크기에 포함**됩니다. 58바이트 고정 헤더 + ID + 메타데이터이고 압축률을 계산할 때 헤더를 제외하는 일이 없습니다. 이 파일 포맷은 프로젝트 전용 포맷이며 표준 `.zip`/`.gz`와 호환되지 않습니다. 코드 구현에는 zlib/gzip/압축 패키지를 사용하지 않습니다. SHA-256은 압축 알고리즘이 아닌 무결성 검증에만 사용됩니다.

## 결과표 계산 공식

| 지표 | 계산 기준 |
| --- | --- |
| 용량 절감률 (%) | `(1 - 실제 .huf 크기 / 원본 크기) × 100` (음수면 오히려 커진 것) |
| 압축 배율 | `원본 크기 / 실제 .huf 크기` |
| 파일 평균 비트 수 | `실제 .huf 크기 × 8 / 원본 바이트 수` |
| 페이로드 평균 비트 수 | `패딩 제외 압축 유효 비트 수 / 원본 바이트 수` |
| 엔트로피 H(X) | `-Σ p(byte) × log2(p(byte))` (bit/byte) |
| 엔트로피 초과 비트 | `실제 페이로드 평균 - H(X)` |
| 엔트로피 대비 효율 (%) | `H(X) / 페이로드 평균 × 100` (분포 변화가 있는 FGK에선 100%를 넘을 수도 있으므로 참고값) |
| 헤더 비중 (%) | `헤더 크기 / 실제 .huf 크기 × 100` |
| 손실 바이트 수 | `원본·복원 파일에서 위치별 다른 바이트 + 길이 차이` |
| 손실률 (%) | `손실 바이트 수 / max(원본 크기, 복원 크기, 1) × 100` |
| 처리 시간 | `perf_counter()` 측정 (파일 읽기/쓰기 포함) |
| 처리량 | `원본 바이트 수 / 처리 시간 / 1,048,576` MiB/s |

- **손실률 0.000000%**는 `압축 + 복원 + 검사`에서 별도 복원 파일을 만든 뒤 원본과 바이트 단위 비교하여 확인합니다. **파일 손실 0과 압축률 증가는 별개의 값**입니다.
- 원본 파일이 없는 **독립적인 복원**에서는 헤더의 SHA-256과 크기 검증은 수행하지만, 손실률은 **'—'**로 표시합니다. 원본과 직접 비교하지 않고 손실률 0%라고 주장하지 않습니다.
- **빈 파일**은 엔트로피와 평균 비트를 0으로 놓고 비율이 정의되지 않는 값(용량 절감률 등)은 `—`로 표시합니다. 작은 파일은 헤더 때문에 오히려 크기가 늘어날 수 있습니다.
- 비트 단위 압축의 평균 코드 길이(Huffman)과 **헤더를 포함한 파일 평균 비트 수**는 구분합니다. FGK는 신규 심볼 NYT+8비트를 포함한 페이로드 실제 비트 수를 사용합니다.
- 손상된 파일(MAGIC, 길이, 패딩, 코드표, 출력 SHA 불일치 등)은 오류로 처리하고, 정확성이 검증되지 않으면 출력 파일을 저장하지 않습니다. 단, **내가 작성한 알고리즘의 자동 비교실험**에서는 복원 바이트가 달라도 오류로 중단하지 않고 실제 손실률/차이 바이트 수를 결과표에 **FAIL**로 남기며, 손상된 복원 파일은 저장하지 않습니다.

## 발표 실험 권장안

12개 샘플을 두 알고리즘으로 실행하면 총 **24회** 실험입니다. 각 파일의 원본 바이트 수/바이트 종류/엔트로피/절감률/헤더 비중/압축 시간/복원 시간을 CSV로 저장합니다. 압축률에는 헤더 비용이 포함됩니다. 정확성 검증은 전부 PASS(손실률 0%)여야 합니다. 실제 측정 시간은 CPU·저장장치·Python 버전에 따라 달라지므로 장비 사양과 Python 버전도 함께 보고서에 기록하세요.

**보고서 그래프 4종 추천:** (1) 문자 수별 압축 시간, (2) 분포 유형별 실제 절감률, (3) 엔트로피와 페이로드 평균 비트 수, (4) A/B 알고리즘의 파일별 압축 및 복원 시간. 연속 실험 3회 이상 반복하여 평균/표준편차를 기록하면 성능 비교의 신뢰도가 높아집니다.

## 안전/예외 처리 및 한계

- 기본 입력 단위는 **바이트 0~255**입니다. UTF-8 한글은 문자당 여러 바이트가 될 수 있어 문자 엔트로피가 아니라 바이트 엔트로피가 출력됩니다.
- SHA-256 검증 및 파일 전체 메모리 처리 때문에 현재 구현의 파일 크기 안전 상한은 **512 MiB**입니다. 과제의 500,000자 파일은 이 범위에 포함됩니다.
- `FGK`는 이해와 검증에 초점을 둔 Python 구현으로 순수 파이썬에서 정적 허프만보다 느릴 수 있습니다. 입력이 크면 완료 시간이 길어질 수 있습니다.
- 압축 입력 파일을 우발적으로 덮어쓰지 않도록 경로 검사를 합니다. 복원 전에 SHA 검증을 통과해야 원자적 쓰기로 파일을 저장합니다.
- 반복 실험의 평균 통계는 각 파일을 1회 측정한 값의 산술 평균입니다. 여러 반복의 표준편차는 별도 반복 실행/CSV 집계가 필요합니다.
